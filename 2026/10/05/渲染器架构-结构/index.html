渲染器架构{1}-结构

2026年10月05日 4.3k 字 大概 19 分钟

现代渲染是一个 CPU 和 GPU 共同协作的过程. CPU 端往往需要保证将各种资源按照一定的规则传递给 GPU, 而在 GPU 端往往通过 Shader 来实现具体的算法和效果. 对于 CPU 端, 其主体往往分为三个层面: 业务侧面, 渲染侧面 和 RHI 侧面. 这里指代的渲染侧面和业务侧面, 可以理解为实际执行渲染的模块和执行游戏逻辑的模块.
业务层负责提交渲染意图, 渲染层用于和 GPU 进行实质交互. 对于三个侧面, 分别代表三个线程(有时渲染线程和RHI也可以是一个线程, 将其分开是UE的策略):

  • 业务层面: 负责提交渲染意图, 这里的渲染意图可以有若干种具体的实现, 可以将其封装为一个 RenderRequest 对象, 内部存一个当前渲染请求的类型和一个由业务线程指定具体的回调函数(UE实际上就是这么实现的, 但是其没有封装 RenderRequest 对象). 这里需要注意线程同步的时候对共享对象的访问, 此时在渲染线程中会直接拷贝一份对象中重要信息来避免对共享对象的访问. 同时在一帧当中会有很多次渲染意图的提交, 但是本质上都是数据的更新, 之后在本帧的最后业务线程(往往是摄像机组件)会提交一次真正的渲染请求.
  • 渲染层面: 渲染线程在收到渲染请求时, 此时往往是业务线程的一帧的最后一个请求. 此时渲染线程开始基于所有更新的数据来录制提交给 RHI 线程的绘制命令. 这其中基本包括
    • 构建视图数据和计算每个视图的可见性
    • 构建 PSO 数据
    • 构建, 编译, 执行渲染依赖图. 渲染依赖图执行完之后就得到了已经录制好的渲染命令
  • RHI层面: 在收到渲染线程提交的渲染命令之后, 通过动态派发走进对应的API分支, 然后解析渲染命令最后向 GPU 发送绘制调用.

对于上述的三个线程, 以下称之为 Game线程, 渲染线程 和 RHI线程.

[!note] 三个线程的数据流
一帧内数据在三个线程之间单向流动:
Game 线程(更新场景数据, 提交渲染意图) → 渲染线程(可见性, PSO, 构建并执行 RDG, 录制命令) → RHI 线程(把平台无关命令转译为具体 API 调用) → GPU。
线程之间通过命令队列与同步原语(如 Game 线程的 FrameEndSync)解耦, 从而允许流水线式并行, 避免某一方阻塞拖慢整帧。

对于 GPU 端, 这里特指基于光栅化渲染关系的渲染器, 开发者至少需要实现两种 Shader: Vertex Shader 和 Pixel Shader.
Vertex Shader: 顶点着色器主要的功能是处理顶点属性, 并将处理完之后的顶点属性传递给下一个阶段
Pixel Shader: 像素着色器往往位于光栅化之后, 是给每一个像素上色的着色器, 这里也是主要算法实现的地方.

对于像素着色器来说, 其本质是一个数学公式: 输入 CPU 侧传来的数据, 再辅以基于物理的公式, 计算出每个像素的最终颜色——这正是基于物理的真实感渲染(PBR)的核心, 具体内容见下一篇”原理”笔记.

离屏渲染请求

在实际的游戏场景中, 往往会有各种画中画的场景, 例如: 狙击镜开镜, 小地图, 透光的且映照出内部场景的窗户等等. 面对这种情况, 现代渲染器可能会选择将这个场景单独渲染成一张 RenderTarget, 最后再将 RenderTarget 独立的渲染在屏幕中.
这里说的 RenderTarget 实际上是一种离屏渲染, GPU将图形绘制到一个独立的 Image 上, 然后再贴到屏幕上, 这种情况称这张图为 RenderTarget.
而且 RenderTarget 的渲染是独立于主屏幕的, 所以可以实现以上的画中画的效果. 在 UE 中该方式对应的 Component 为 USceneCaptureComponent, 其并不是 UPrimitiveComponent 的派生类, 而是独立的.
对于这种情况, 会有一个标志bRenderInMainRender

  • true: 作为主渲染视口的一部分, 其会作为一个附加 Pass 在主渲染器的流程中, 通过优先级决定谁先谁后.
  • false: 独立渲染窗口, 其会先绘制所有的 USceneCaptureComponent 请求的画面至一个离屏的 RenderTarget 上, 然后绘制主屏幕上的场景至 BackBuffer 中, 最后在绘制 UI 时使用 Image 控件对 Render Target 进行采样

渲染线程

在渲染线程这一侧, 我们主要讨论 Render() 被调用时具体发生了什么, 其更能体现出渲染侧面的整体架构. 在实际的光栅化渲染器设计中, 主要需要处理两个点:

  1. 材质
  2. 渲染通道

这两点在后面的 Render 流程中分别对应: “材质”最终落地为 MeshDrawCommand 与 PSO 的构建(ProcessXxxMesh 阶段); “渲染通道”则对应各个 RenderXxx Pass 以及 RDG 对 Pass 的编排。

其实上述的一切流程都是基于现代图形API展开的, 或者说站在现代图形API的角度理解会更自然. 以下以Vulkan为例:

现代图形API的两个核心概念是 Pipeline 和 RenderPass, 其分别代表着光栅化图形流水线, 以及一次渲染中帧缓冲的布局(由哪些附件组成, 分几个子通道, 子通道之间如何依赖). 即现代API将”流水线(Pipeline)”和”帧缓冲布局(RenderPass)”解耦. 所以在渲染器的实现中往往也会将这两个对象分开处理. 其中,

  • Pipeline 本身是一个巨大且笨重的对象, 无法做到随时创建和随时使用, 所以对于 Pipeline 渲染器会提前创建好并缓存起来(甚至缓存到文件中), 在使用 Pipeline 时再查找缓存, 如果没有才会进行创建.
  • RenderPass 描述的是帧缓冲由哪些附件组成, 分几个子通道, 子通道之间如何依赖

RenderPass 和 Pipeline 并没一一对应关系. 例如: 对于一个延迟着色流程, 往往会分为两个过程: 几何Pass 和 光照Pass. 其中光照Pass 依赖于几何Pass 产生的 GBuffer. 所以这里定义一个 RenderPass 的两个 SubPass(也可以独立定义两个RenderPass然后中间插入一个屏障, 一个RenderPass 带两个 SubPass 更高效), 第一个子通道写入多个GBuffer(颜色, 法线, PBR属性), 第二个子通道使用这些GBuffer作为输入附件进行光照计算. 对于 Vulkan 来说, 即 第一个子通道输出到多个颜色附件和深度/模板附件, 第二个子通道将这些颜色附件作为输入附件最后输出颜色附件.

[!note] 附件
在 Vulkan 中, 附件本质就是一张图, 颜色附件就是存有 RGBA 的图, 深度附件就是记录深度信息的图, 其本质是就是若干带有信息的矩阵.

需要澄清的是, 上述 VkRenderPass 的创建只是声明了这些 GBuffer 附件的格式与布局(在 VkAttachmentDescription 的 format / initialLayout / finalLayout 里), 它并不会真正创建 GBuffer 图像本身——GBuffer 对应的 VkImage 需要单独创建, 并绑定到帧缓冲(Framebuffer)上才能使用。而着色器如何访问这些 GBuffer(作为 input attachment 还是采样纹理, 绑定到哪个 binding), 则是在 Pipeline 关联的 VkDescriptorSetLayout(VkDescriptorSetLayoutCreateInfo)里声明。

换句话说: VkRenderPass 描述的是”帧缓冲由哪些附件组成, 各附件是什么格式和布局, 分几个子通道, 子通道之间如何依赖”; VkDescriptorSetLayout 描述的是”着色器里通过哪些 binding 去读这些资源”。两者是不同层面的东西。同样地, 更复杂的场景也会使用到更复杂的 RenderPass 和 Pipeline 之间的对应关系.
而现代渲染器流程正是在 CPU 端区别了 RenderPass 和 Pipeline 这两个流程. 其主要实现方式是渲染依赖图 RDG(见具体章节).

RHI 线程

正如之前所言, RHI 单独开一个线程并不是必须的. 但是如果像 UE 一样选择开一个新的线程, RHI 线程的功能是将渲染线程录制的命令转义为 GPU 能识别的格式, 其核心是将各个平台的 API 用统一接口进行分发. 从而实现跨平台.

RHI 线程的核心职责可以进一步拆分为:

  1. 命令分发: 渲染线程录制的是平台无关的渲染命令(FRHICommandList), RHI 线程通过动态派发把每条命令转译成具体图形 API 的调用(DX12 的 CommandList / Vulkan 的 vkCmdXxx / Metal 的 MTLCommandBuffer)
  2. 资源管理: 统一封装各平台的资源对象(纹理, 缓冲区, 采样器, PSO 等), 对外暴露同一套 RHI 接口
  3. PSO 管理: 负责 Pipeline State Object 的创建, 缓存与查找(现代 API 中 PSO 是重量级对象, 需要预先创建并缓存)
  4. 内存与屏障: 处理资源的布局转换(layout transition)与内存屏障, 保证 GPU 上资源访问的正确性

把 RHI 单独拆成线程, 本质是让渲染线程专注于”编排”渲染流程, 而把平台相关的”翻译”工作交给 RHI 线程, 从而屏蔽不同图形 API 的差异, 实现跨平台。这也是为什么渲染线程录制的命令需要是”平台无关”的抽象命令。
